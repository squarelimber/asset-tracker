## 1. 结论

**App 显示 +104.30 元，实际约 +4,900 元，少算约 4,800 元。**

根因是 **快照口径的两天基准不统一**：`todayEarningOf` 用"昨天的快照"作为今天的基准，而 9-15 那条快照是**昨天盘中 13:45 用实时行情写的**，不是收盘价。9-15 当天全线高开低走，基准被抬高 → 今天的收益被压低。

叠加第二个因素：**场外基金净值 T-1 滞后**，9-15 的基金跌幅被记进了 9-16。

## 2. 对账（全部为实测，非推算）

### 2.1 快照的写入时刻 —— 两个口径的源头

| 日期 | totalValue | createdAt | 写入方式 |
|---|---|---|---|
| 2026-09-07 ~ 09-14 | 各不同 | **全部 = 2026-09-15T10:28:20** | 同一次全量回填（收盘价口径） |
| 2026-09-15 | 2193378.0355 | **2026-09-15T13:45:00** | 前一天**盘中**实时刷新 |
| 2026-09-16 | 2193482.3349 | **2026-09-16T14:03:39** | 今天**盘中**实时刷新 |

`profit(d) = totalValue + liabilities − totalCost`：

- profit(9-14) = 32,967.4666（回填，收盘价）
- profit(9-15) = 33,643.6175（盘中 13:45）
- profit(9-16) = 33,747.9169（盘中 14:03）

→ App 的"今日收益" = 33,747.9169 − 33,643.6175 = **+104.2994**

### 2.2 快照值已完整复现

用备份里 holdings 的 `quantity × latestPrice` 求和：

→ `netWorth = 2,193,482.3349`，与 9-16 快照 `totalValue` **逐位一致**，确认计算模型理解无误。

## 3. 根因（代码级）

### 环节 1：每次刷新成功都会用实时价重写当天快照

`lib/ui/pages/portfolio/portfolio_page.dart:101`
```dart
if (result.allOk) {
  await ref.read(snapshotServiceProvider).ensureTodaySnapshot(force: true);
}
```
用户在 9-15 13:45 的最后一次刷新，把 9-15 永久定格在了 13:45 的盘中价。

### 环节 2：回填之后又被实时价覆盖（设计冲突）

`lib/app/providers.dart:138`
```dart
if (!result.historyUnavailable) {
  await ref.read(snapshotServiceProvider).ensureTodaySnapshot(force: true);
}
```
而 `HistoryBackfillService` 的文档注释明确写着：

> The window **includes today**. … Re-deriving today from the same series makes the two paths agree by construction.

回填刚用"与历史相同的价格序列"写好今天，紧接着又用实时价覆盖 —— **注释宣称的一致性被这行抵消了**。

### 环节 3：回填不修正"昨天"（关键）

`lib/services/history_backfill_service.dart:220-228`
```dart
final existingDates = <String>{};
if (!needFullRebuild) {
  existingDates.addAll((await _dao.getSnapshots()).map((s) => s.date));
}
existingDates.remove(todayKey(todayDate));   // 只移除今天
```
轻量回填**只重算今天**。昨天（以及更早的"盘中定格日"）永远不会被收盘价修正，除非触发 `forceRebuild`。而 `forceRebuild` 只由数据被编辑（`history_sync_dirty`）或首次运行触发。

### 三个环节合起来

```
9-15 10:28  启动 → 全量回填 → 9-07~9-15 全部用历史日线（收盘价）✅
9-15 13:45  下拉刷新成功 → force 重写 9-15 → 定格在 13:45 盘中价 ❌
            （此后 9-15 再无刷新 → 错误值永久保留）
9-16 14:03  刷新 → 写 9-16（实时价，基金取到 9-15 净值）
            → 今日收益 = V(9-16盘中) − V(9-15盘中13:45) = +104.30
```

**正确算法应该是 `V(9-16) − V(9-15收盘)`。**

## 4. 影响范围

- **不止今天**：任何"当天最后一次打开 App 是在盘中"的日期，其快照都定格在盘中价，会污染**次日**的今日收益。
- **对含场外基金的组合更严重**：基金净值 T-1 滞后，每天都会把前一天的基金涨跌记到当天（9-16 被记进 −2,170）。
- **同一个日期、两个数字**：总览卡与日历格走快照口径，日历里点开的持仓明细走历史口径 —— 用户能直接看到自相矛盾的两个数。
- 与 v0.9.7 修过的"周末收益异常"是**不同**问题：那次是黄金双源 + 交易时段门控；这次是快照基准时刻不一致。

## 5. 修复建议

### 方案 A（推荐，最小改动）：回填时同时修正"昨天"

`lib/services/history_backfill_service.dart:228`
```dart
existingDates.remove(todayKey(todayDate));
// 新增：最近一个已收盘的交易日也要重算——它的快照可能是在盘中
// 用实时价写的，且当天场外基金的"最新净值"还停在 T-1。
final yesterday = todayDate.subtract(const Duration(days: 1));
existingDates.remove(todayKey(yesterday));
```
理由：昨天的历史数据已定稿（收盘价 + 当日净值），重算一定比盘中价准，且能把基金净值归位到正确日期。周末场景安全（`priceOnOrBefore` 会回落到最近交易日）。成本：每次多算 1 天。

### 方案 B（配套）：去掉回填后的无条件实时覆盖

`lib/app/providers.dart:139` 的 `ensureTodaySnapshot(force: true)` 应仅在回填**没有**写今天时才执行（例如 web 平台或回填被跳过）。

### 方案 C（正交，彻底）：区分"临时快照"与"定稿快照"

快照加 `provisional` 标记：当天盘中写的是临时值；收盘后/次日回填定稿。`todayEarningOf` 在基准日为 provisional 时回落到实时口径。

### 方案 D（治本方向）

`todayEarningOf` 与日历当天格统一改用**历史序列口径**（即 `HoldingDetailService` / `ProductEarningsService` 那套，已用收盘价且能处理买卖），快照只作为趋势图的粗略来源。"快照相减"无法表达"今天 vs 昨天收盘"这个语义。

### 建议优先级

1. 先上 **A + B**（改动小、立刻消除基准错位，且次日自愈）
2. 基金滞后：在界面注明"基金部分为 T-1 净值"，或在快照里显式标注口径

## 6. 已存在错误快照的补救

9-15 已被定格，需要一次全量重算才能修正：

- 编辑任一持仓（例如改备注再改回）→ 置 `history_sync_dirty` → 下次启动触发 `forceRebuild` → 全量重算
- 或用设置页新增的「重建历史快照」入口（见下）

重算后 9-15 回到收盘价口径，9-16 的今日收益随之回到正确量级。

## 7. 修复实施（2026-09-16，方案 A+B+C）

### A — 回填把「上一次运行以来」的每一天都重算

`lib/services/history_backfill_service.dart`

- 新增 setting `backfill_last_run`（记录上次成功运行日）；轻量回填时把 `[上次运行日, 今天]` 全部移出 `existingDates`，成功后写入本次运行日。
- **为什么不是"只补昨天"**：昨天之后也能被修复，是因为每次启动都会跑；一旦 App 隔了 10 天才再打开，被盘中价定格的那天就在 10 天前，固定「今天 + 昨天」的窗口会**永远漏掉它**。锚定上次运行日后，任何长度的空档都能覆盖，且锚点前的日子（用户手动改过的值）依旧不动。
- 环境不变量：锚点只在快照**换入成功之后**写入，所以一次中止的运行不会让待修的日子被跳过。

### B — 回填后不再无条件用实时价重写今天（方案已更正）

`lib/app/providers.dart`

> **本报告 §5 原先写的方案 B「回填写了今天就不再覆盖」是错的。** `SnapshotService.ensureTodaySnapshot` 的文档明确要求 `force` 只能在报价**确认新鲜**时传入（"a rewrite from stale prices replaces a correct figure with a wrong one"），而 `historySyncProvider` 这条路径**不做任何行情刷新**——回填的今天是由与历史同一条价格序列推出的、一致的值，用未经验证的缓存报价去覆盖它才是反向的。
> 不过 `providers.dart` 那行确实是缺陷：它违反了 `SnapshotService` 的调用契约。

实际实现：`BackfillResult` 新增 `wroteToday`；仅当回填**没有**写今天（web 平台、或抓取失败）时才走兜底写入。今天仍由**行情刷新闸门**负责——`portfolio_page` 在 `result.allOk` 后重写，那才是被 `SnapshotService` 承认的合法调用点。

### C — 设置页「重建历史快照」

`lib/ui/pages/settings/settings_page.dart`

- 放在既有「数据备份」卡片里作为**第三行**：不新增分区标题、不新增卡片、不新增一排按钮，避免页面继续变长。
- 交互：二次确认弹窗 → 不可取消的进度弹窗 → SnackBar 反馈结果。
- 执行：`backfill(forceRebuild: true)` → **先刷新行情**、仅 `allOk` 时重写今天（与 portfolio 页同一条闸门）→ `invalidate(cnyRatesProvider)`。
- web 平台隐藏该行（`kIsWeb` 下回填本就不支持）。

## 8. 追加排查：用户反馈「今天盘中时昨天收益也会变」（2026-09-16 15:00）

用户补充观察：在 9-16 盘中，收益日历里**昨天（9-15）那一格**也会变化。把四条可能的代码路径逐一查完：

| 路径 | 9-15 的值会变吗 | 机制 |
|---|---|---|
| 日历格 — `daily_earnings.dart` + `DailyEarningsCalculator` | **否** | 快照相减。`watchSnapshots` 已 `orderBy(OrderingTerm.asc(t.date))` 且 `currency: 'CNY'` 过滤，相邻日配对不会错位 |
| 日期明细 — `holding_details.dart:190-233` | **否** | 只有 `_isSameDay(day, DateTime.now())` 成立（即 day 是今天）时才 `price = h.latestPrice`；历史日一律走 `priceOnOrBefore`，且 `prev` 也取自历史序列 |
| 产品收益日历 — `ProductEarningsService.compute` | **否** | 纯 `adapter.fetch(symbol, from, current)` + `HoldingReplay`，历史日走 `filler.priceOnOrBefore(key)`；`ProductEarningsCalculator` 的 `curQ * curU` 来自 replay，不含当前市价 |
| **热力格颜色** — `heat_cell.dart` → `T.heat(value, min, max)` | **是** | 颜色按**当月 min/max** 归一化。今天那格数值在盘中大幅变化 → 当月 `maxProfit` 变化 → **全月所有格子（含昨天）的颜色重新映射** |

### 硬证据：历史快照在 9-16 盘中未被改写

备份 `createdAt` 分布：

| 日期 | createdAt | 性质 |
|---|---|---|
| … 9-14 | 全部 `2026-09-15T10:28:20` | 同一次回填 |
| 9-15 | `2026-09-15T13:45:00` | 单独一次写入（盘中定格） |
| 9-16 | `2026-09-16T14:03:39` | 实时快照写入 |

回填写入时**所有行共享同一个 `createdAt`**。因此若 App 在 9-16 盘中重算过历史，9-14 及之前的时间戳会**集体前移**。实测全部仍是 `2026-09-15T10:28:20` ⇒ 9-16 盘中**没有发生历史重算**，9-15 那条自 `13:45:00` 起未被触碰。

> 可复用判据：**「`createdAt` 是否集体更新」= 「历史是否被重算」**。一次全量重建表现为"同一天数批次、同一秒、覆盖全部日期"。

|---|---|
| 9-15 | **+676.15** |
| 9-16 | **+104.30** |

若手机日历页 9-15 格显示的不是 `+676.15`，说明数据被改写，需进一步定位。

用户看到的"昨天收益变化"是**数字**变化还是**颜色深浅**变化：

### 预测偏差的诚实说明

- **9-15 我预测 −1,300，实际 −3518。** 原因是 §8 的推算**漏了一项**：我只补了「13:45 → 收盘的 ETF 回落（+2,070）」，却忘了旧快照的**基金部分用的是 9-14 净值**，而新快照用 9-15 净值，这一项还要再补 **−2,170**。正确算式是 `676.15 − 2,070 − 2,170 = −3,564`，与实际 −3,518 吻合。**是推算漏项，不是模型错误。**

### 残留风险（重要）

① **盘中执行「重建历史」仍会复现本 bug。** 9-16 那条的 `createdAt` 是 `15:16:22`，比其余 2237 行晚 2 秒 —— 说明重建后它**又走了 live-quote 路径重写**（旧版 `portfolio_page.dart:101` / `providers.dart:139` 的行为）。本次因为 15:16 已收盘、实时价 = 收盘价，所以无害；**但若在盘中重建，"今天"会被再次定格在盘中价**，明天继续少算。⇒ 这正是修复方案 **B** 要消除的。

② **新版首次运行存在一天错位窗口。** A 方案的实现是 `var reopenFrom = lastRun ?? todayDate;` —— 用户设备上 `backfill_last_run` 尚不存在，**首次运行只重算当天、不回看昨天**。若用户今晚不刷新，9-16 会停留在「用 9-15 净值」的版本；9-17 的快照取到 9-16 净值，于是 **9-16 的基金涨跌会被记进 9-17**，错位重演。⇒ 建议把首次运行的回退改为至少回溯一天（或首次直接触发全量重建）。

③ **今晚净值发布后建议再刷新一次**，把 9-16 补成含 9-16 净值的正确版本；届时 9-16 格会小幅变动（增加当日基金涨跌），**这属正确行为**。

## 10. 收尾：残留风险 ② 的加固与发布（2026-09-16，v0.9.9）

### 10.1 加固「首次运行」

§9 残留风险 ② 指出：A 方案的实现是 `var reopenFrom = lastRun ?? todayDate`，用户设备上 `backfill_last_run` 不存在，**首次运行只重算当天、不回看昨天**——刚修好的错位会在升级后的第一天重演。现改为向后取固定窗口：

```dart
static const _firstRunLookbackDays = 7;

var reopenFrom = lastRun ??
    DateTime(todayDate.year, todayDate.month, todayDate.day - _firstRunLookbackDays);
```

取 7 天是为了覆盖"周末 + 假期"这一最长常规空档；代价极小（同一条价格序列多跑几天逐日循环）。随之而来的效果是：**升级设备在首次启动时就会自动修好窗口内的定格日**，不必依赖用户手动点「重建历史」。

配套回归测试 `test/history_backfill_test.dart` → `a light run with no previous-run anchor`：一次性造出"标记已置位但无 `backfill_last_run`"的升级态，断言窗口内（含边界日 `today - 7`）的定格值被重算、窗口外一天的值原样保留。
